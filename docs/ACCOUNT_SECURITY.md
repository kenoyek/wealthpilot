# Account and security controls — 2026-10-28

Settings now offers a complete workspace export, password-confirmed sign-out of all device sessions, and a separate explicit account deletion flow. Android remains paused. This phase uses the existing Vercel/Neon deployment; no staging, storage provider, paid service, MFA or passkey implementation is added.

## Complete export

The same-origin POST download route requires the current password, an active workspace and a shared database-backed security-attempt allowance. It obtains a two-minute single-use server capability before calling the export RPC; a session alone cannot invoke the bulk export. The fixed 22-table workspace allowlist covers profiles, accounts, categories, full entries/lines, budgets, audits, planning requests, goals/events, commitments/prices/payments, debts/payments, allocation batches/templates, recurring schedules/occurrences and import receipts/identities. A stable private SQL function reads them in one statement snapshot, with explicit owner predicates, without API row-limit truncation. Decimal and bigint columns become strings. The JSON download includes the signed-in email/verification status; sign-in passwords, provider session tokens, verification codes and application signing configuration are excluded.

The server preserves the returned JSON text instead of parsing/re-serializing database numeric fields. JSON or gzip is offered; downloads over 2 MB of raw JSON compress automatically. A payload still over 4 MB after compression fails explicitly with no records omitted. This transport limit is stated in the UI; larger transfers need a future transfer mechanism. Downloads are private/no-store and not persisted in cloud storage. Monthly report CSV remains available.

## Fresh authentication and sessions

Current-password checks use the provider's own credential sign-in implementation and verify the returned identity matches the requesting session; the application never reads or stores password hashes. The local fixture uses Supabase credentials, production Native Neon Auth. Five security confirmations per 15-minute fixed window are enforced in a protected DB table across app instances. This applies to export, password change, session revocation and account deletion. It complements existing per-process public auth burst guards/provider limits; it is not a claim of a distributed public-login lockout system.

Password creation/change/reset bounds are consistent at 12–128 characters. Changing the password retains Neon's revoke-other-sessions behavior. The new explicit all-device action calls the provider's global session revocation, then signs the current browser out. Native session metadata cookies use a 30-second cache instead of five minutes; previously issued cache cookies expire under their original TTL. Already issued direct Data API JWTs may remain cryptographically valid until expiry. Account closure additionally blocks those JWTs at the DB identity layer, independent of the session cache.

The generic auth proxy now allows only session/token maintenance and sign-out routes. Credential/account mutations use validated server actions rather than a raw proxy bypass. This does not remove the provider's own public authentication API or replace provider abuse controls. Complete-export POSTs validate the browser Origin against the external Host, including reverse-proxy deployments; cross-site, malformed, credential-bearing and insecure non-local origins are rejected.

## Explicit deletion and failure handling

Deleting is never part of rollout/testing against a real account. The person must open the deletion page, enter the current password and type `DELETE MY ACCOUNT` exactly. The app captures a short-lived authenticated cleanup credential before purging. A signed, owner/purpose/time/nonce-bound capability authorizes the atomic financial purge. It is not possible to request another person's purge by supplying their ID, or to bypass fresh authentication by calling the purge RPC with only a session.

The atomic purge marks the workspace closed and removes all current workspace records in dependency order. Production keeps the internal identity mapped temporarily but `current_user_id()` returns null for a closed, unverified or removed provider identity. `ensure_application_user()` recognizes closure and never initializes a replacement workspace. Consequently an old JWT cannot recreate data after closure. Local deletion fixtures remove only their own disposable Supabase identity atomically via a private fixture hook; the native hook leaves identity removal to Neon Auth's official SDK.

The app then invokes Native Neon Auth's `deleteUser({password})`. After the provider identity is absent, the signed authenticated finalizer removes the temporary internal mapping/closure state. It refuses to finalize a still-existing provider identity. If the provider step fails, the already-removed workspace remains closed and the existing identity can sign in only to retry deletion, not access/recreate finances. If the final cleanup request fails, an AES-256-GCM encrypted, HttpOnly/Secure/SameSite=Strict receipt holds the closed account's short-lived cleanup JWT for retry. It is never returned in the export or page markup. The JWT cannot access a closed workspace. The receipt lasts at most 24 hours, but retries require that JWT to remain valid; an expired cleanup credential requires support to remove minimal residual closure metadata. A successful finalizer clears the receipt. No background cleanup service or external administrator credential is deployed.

The Data API requires JWT authentication, so finalization uses the captured authenticated JWT and a fresh server capability, not an unsupported anonymous SDK request. Native SQL compatibility tests explicitly exercise closed-subject JWT finalization after provider removal. No unauthenticated production mutation probe or actual production deletion is part of verification.

Deleting the app account does not cancel bank accounts, bills or external payments. Primary workspace removal is immediate on success; backups/provider logs may retain copies until their normal retention expires. The UI explains these limits before confirmation.

## Capabilities and rollout

Shared migration `202610280015_account_security.sql` creates the protected configuration, closure, security-attempt and consumed-nonce tables plus owner-scoped metadata/export/purge/finalization functions. Private tables/functions are inaccessible to API roles. Server capabilities use a dedicated 32-byte secret with HMAC-SHA256; PostgreSQL's implementation uses built-in SHA256 and is checked against Node's HMAC implementation. Purpose, owner, issued time and nonce are bound; proofs expire after two minutes and cannot replay. The stable export reader is private; its public wrapper consumes a valid export capability first.

Neon incremental `202610280016_account_security.sql` supplies native identity hooks and closure-aware mapping. It does not alter Neon-managed Auth tables or install provider triggers. `setup-security-production.py` initializes/reuses the protected key and writes the same value as an encrypted Vercel server-only environment binding. It never prints the value and never rotates an existing key on retry. No DB administrator/management credential is added to app runtime. Keep this key stable while deletion receipts are pending; rotation would invalidate those receipts.

Local setup: after migrations, run `node scripts/setup-security-local.mjs`. `env:local` also invokes it for a fresh local configuration. The helper refuses hosted DB bindings, writes only the ignored local env file and local fixture DB, and prints no key material. Production deployment validation now requires the server-only capability key.

## Import limit correction

A large-export fixture exposed that the existing 60-posts/minute manual throttle also blocked legitimate large CSV batches and grouped undo. Shared migration `202610280017_bounded_imports.sql` adds a private transaction-scoped bulk registry that only import/undo functions can open. Those operations allow at most 200 ledger writes per batch and 1,000 owner writes/minute. Other posting paths retain the existing 60/minute limit. The private context is removed on success or rolls back with a failed transaction. Authenticated API roles cannot open it themselves. Tests exercise 200-row import plus 200-row undo on both local and native fixtures and verify ordinary posting remains throttled.
