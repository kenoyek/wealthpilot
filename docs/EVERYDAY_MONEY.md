## Recurring schedules

- Income and expense templates support weekly, monthly, quarterly and yearly schedules. Each has an owner, account, matching-scope category, amount, description, next due date and stable month-day anchor. Month-end dates clamp for February and return to the original anchor in March.
- Creating/editing/pausing/resuming a template never posts money. A user explicitly confirms an actual transaction date through their profile-local today, or skips an occurrence. Each confirmation advances exactly one occurrence, including an overdue one; it does not silently backfill missed months. Early confirmations require an actual payment, not merely an upcoming due date.
- `resolve_recurring` uses the existing balanced ledger RPC, owner advisory lock, request idempotency and a revision check. A unique owner/template/due-date constraint protects each occurrence. Concurrent confirmations cannot double-post. Stale edited forms fail safely and must be refreshed. Occurrences remain auditable after a schedule is edited.
- Reversals use the existing Transactions correction workflow and do not rewind a recurring schedule. A recurring shortcut does not reserve funds or duplicate commitments in cash forecasts: use Bills & subscriptions for planned unpaid obligations and record each actual payment once.

## CSV import

Download `/wealthpilot-import-template.csv`, an empty UTF-8 CSV header template. Required headers are `date,type,amount,description`; optional `reference`. Headers can be reordered and are case-insensitive. The importer supports quoted commas, doubled quotes, embedded newlines, CRLF/LF/CR line endings and a UTF-8 BOM. Dates must be real ISO `YYYY-MM-DD` dates through today, types `income`/`expense`, amounts positive plain decimals with the selected account's currency precision. Transfers, refunds and opening balances use the regular transaction form. This is a documented format importer, not automatic recognition of arbitrary bank layouts.

Choose one account and one category for each transaction type present in the file. Categories must belong to the current user and match that account's scope and the row type. Import other currencies/accounts in separate batches. Maximum 200 rows and 256 KiB per file/request. Descriptions are limited to 500 characters, references 160. Invalid UTF-8 uploads, malformed quoting, unknown/duplicate headers, mismatched column counts, invalid dates, signed/scientific/formula amounts and binary/NUL content are rejected. Description text is never evaluated as spreadsheet code; existing CSV exports escape formula-like text.

Preview parses/validates on the server and uses a read-only database branch to check stored duplicates. It shows exact amounts and per-row outcomes without posting entries. The client prevents the form's automatic reset so reviewed selections survive to confirmation; changing inputs cancels the preview and rotates its request key. Failed confirmations retain the source text and selections. A confirmed import is one atomic database transaction; a later invalid row rolls back earlier postings, import identities and the receipt. Repeated request keys return the existing receipt, while changed payloads with the same key are rejected.

Duplicate identity is scoped to user + account. With a reference, that reference identifies the row; changed date/type/normalized amount/description under the same reference is an error, not a silent skip. Without a reference, the normalized date/type/amount/description is the identity. Decimal scale (`10` vs `10.00`) does not create a new identity. Re-uploaded rows, duplicates inside a file and category-only changes are skipped. Two legitimate identical transactions need different references. These checks cover CSV imports only, not separately posted manual or recurring entries. No cross-user duplicate query is possible.

Recent receipts show imported/skipped counts and offer explicit grouped undo. Undo atomically reverses outstanding entries in that batch instead of deleting originals. It skips originals already reversed manually, is idempotent, and respects existing refund rules: reverse an associated refund before undoing its original expense. If one reversal is blocked, the whole undo rolls back. Import identities remain consumed after undo to protect against accidental re-upload; corrected replacements use the regular transaction form.

Raw filenames/files are not retained as uploaded documents. Normalized transactions, deduplication payloads/fingerprints, receipts, occurrence history and financial/request audit records are retained behind owner RLS. Preview data and CSV content are sent only to the app's authenticated server/database, not third-party analytics or a file-processing service.
